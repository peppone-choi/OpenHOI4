## 0. 구조

**현재 실행 경로 — 사용자 지시(2026-10-06).** CEO는 Codex 앱의 `create_thread`로 오케스트레이터 채팅을 하나씩 만들고, 오케스트레이터도 같은 앱 기능으로 구현·검증 채팅을 만든다. 사용자는 이 작업의 CEO·오케스트레이터·구현·검증 채팅 사이 작업 지시·질문·결과 메시지 교환을 허용했다. CEO는 구현·검증 채팅을 직접 만들지 않는다. 이 지시는 아래 CLI 실행 절차보다 우선하며, 초기 결정 질문·권한 범위·독립 검증·진전 및 중지 조건은 그대로 적용한다.

- CEO의 `start/status/wait`는 각각 앱 `create_thread`, `wait_threads(timeoutMs: 0)`, 커서를 사용한 `wait_threads`로 수행한다. 완료는 앱 turn 종료/오류와 `RUN_RESULT`로 확인하고, CLI `exit=0`으로 기록하지 않는다.
- 앱 종료가 CLI 종료 코드를 제공하지 않으면 상태에 `해당 없음(앱 실행)`으로 기록한다. `read_thread`는 결과 전문이나 오류 확인이 필요할 때 사용한다. RUN별 threadId·hostId·커서·최종 확인 시각을 `.orchestrator/ceo/`에 보존한다.
- `ceo_run.sh selftest` 실패는 CLI 경로 증거로 보존한다. 현재 앱 경로의 시작을 막는 근거로 사용하지 않고, 샌드박스·모델·인증 설정을 바꾸지 않는다. 앱 호출과 실제 실행 응답으로 앱 경로를 확인한다.
- 정체 시 앱 채팅에 인수인계와 종료를 요청한다. 기존 오케스트레이터가 실제로 종료된 것을 확인하기 전에는 다음 RUN을 시작하지 않는다. 종료를 확인할 수 없으면 동시 실행을 만들지 말고 상태를 기록한다.
- 구현·검증의 전용 Git worktree와 검증 전후 HEAD·추적 파일 목록·SHA256·diff/status 동일성을 유지한다(02 §12.4, ADR-0001). `orch.sh status`의 과거 CLI 기록과 현재 앱 registry를 함께 대조한다.
- CLI 사용량 오류와 동일하게 앱 사용량 오류도 30분 간격 최대 4회 재시도한다. 실행 중 CEO 기록은 `.orchestrator/ceo/`에만 남긴다.

```
사용자 ── C-01 붙여넣기 ──▶ CEO Codex 세션 (대화형, 1개)
                              │  처음에 질문을 한 번에 묻고, 그 뒤로는 자동
                              │  tools/ceo_run.sh start <RUN>  ← C-02 프롬프트
                              ▼
                       오케스트레이터 실행 (codex exec, 한 번에 1개, 저장소 작업 폴더에서)
                              │  docs/03 P-02 / P-09 절차
                              │  tools/orch.sh start impl|verify
                              ▼
                       구현·검증 세션 (codex exec, WP별 worktree, 병렬 3~4개)
```

- **CEO가 하는 일**: 오케스트레이터 실행을 띄우고, 결과를 직접 확인하고, 다음 실행을 정하고, 결정을 처리하고, 사용자에게 보고한다.
- **CEO가 하지 않는 일**: 제품 코드 작성, 구현·검증 세션 생성. 이것은 오케스트레이터의 몫이다.
- **오케스트레이터 실행은 짧게 끊는다.** 한 번의 실행은 게이트 판정, 병렬 묶음 2개 통합, 결정 대기 중 먼저 오는 지점에서 끝난다. 다음 실행은 `HANDOFF.md`로 이어 받는다(docs/03 P-08·P-09). 그래서 오케스트레이터의 컨텍스트가 길어져 판단이 흐려지지 않는다.

### 1.1 `tools/ceo_run.sh`

| 명령 | 동작 |
|---|---|
| `selftest` | CEO → 오케스트레이터 → 하위 codex 중첩 호출이 되는지 점검 |
| `start <RUN> <프롬프트>` | 오케스트레이터 실행을 분리 시작하고 바로 반환. 다른 실행이 돌고 있거나 이미 쓴 RUN 번호면 거부 |
| `status` | 실행 목록(상태·종료 코드·정체 분)과 `orch.sh status` |
| `wait <RUN> [--timeout 초]` | 끝날 때까지 대기(기본 1800초). 반환값: 끝남 0 / 시간 초과 5 / 프로세스가 사라짐 6. 끝나면 `exit=`과 마지막 메시지를 출력 |
| `idle <RUN>` | 마지막 로그 기록 후 지난 분 |
| `stop <RUN>` | 그 오케스트레이터 실행만 중지. 구현·검증 세션은 건드리지 않음 |

- RUN 번호 형식은 `M<마일스톤>-r<회차>`다. 예: `M1-r1`, `M1-r2`, `M2-r1`.
- 오케스트레이터 샌드박스는 환경 변수 `OH_ORCH_SANDBOX`로 정한다. 기본값은 `workspace-write`이고, 바꾸는 것은 사용자 결정이다.
- 기록은 `.orchestrator/ceo/`에 남는다(git 제외).

## 2. CEO 권한

CEO는 사용자를 대신해 계속 진행시키는 역할이다. 하지만 사용자 결정을 대신 확정하지는 않는다.

**현재 목표 M6의 사용자 후속 지시(2026-10-06).** OPEN 기본안 일괄 적용 승인은 철회됐고 OPEN-01~12의 항목별 실제 답변을 01에 반영했다. 아래 ①을 근거로 그 답변을 덮어쓰거나 아직 없는 세부 규칙을 자동 적용하지 않는다. REQUEST 추천안은 기존 승인 범위·가역성·구체 입력/거부/상태변경/출력·독립 경계 기대값·저장 호환/되돌림 비용을 검토한 뒤 ②로 잠정 채택할 수 있다. 채택 뒤 01에 잠정 규칙과 제작·검증 지시를 기록하고 구현한다. 미완성 후보와 준비 방식 승인은 실제 공식 승인으로 기록하지 않는다. D·OPEN 확정 상태와 사용자 전용 목록은 그대로 사용자 답변이 필요하다.

| 구분 | 내용 |
|---|---|
| **CEO가 해도 되는 것** | ① 01 §9 OPEN의 기본안을 해당 마일스톤에 적용한다(상태는 잠정·미결정 그대로, `REPORT.md`의 "적용한 기본안"에 기록). ② `docs/decisions/` 요청의 추천안을 채택한다. 단, 되돌릴 수 있고, 아래 사용자 전용 목록에 없고, 범위를 바꾸지 않을 때만이다(잠정, "채택한 추천안"에 기록). ③ 정체되거나 실패한 오케스트레이터 실행을 중지하고 재개 실행을 띄운다. ④ 아래 보류 규칙에 따라 다음 마일스톤으로 넘어간다 |
| **사용자 전용** (CEO는 대기 목록에 넣고 보고만) | D·OPEN 상태를 `확정`으로 바꾸는 것(사용자 답이 있을 때만), D-10 라이선스, D-12 공개 명칭, 요청 범위 변경, 복구하기 어려운 삭제, 샌드박스·네트워크·권한 설정 변경, 공개 배포·태그·저장소 공개, 비용 발생, 법적 판단, AGENTS.md 절대 규칙 변경 |
| **CEO가 하지 않는 것** | 제품 코드 수정, 구현·검증 세션 생성, 게이트 판정을 대신 내리는 것, 테스트·검사 완화, 오케스트레이터 실행 중 추적 파일 수정 |

**보류 규칙.** 게이트의 어떤 AC가 **사용자 전용 결정 때문에만** 통과하지 못하면 그 AC는 `보류(사용자 결정)`로 둔다. 다른 AC가 모두 PASS라면 다음 마일스톤으로 넘어간다.

- 해당 예: AC-M3-06 공개 게이트(D-10·D-12), 그리고 AC-M3-07 중 REQ-LEG-07 부분.
- 보류 상태에서는 공개 배포를 하지 않는다.
- 보류 항목은 마지막 보고에 반드시 넣는다.

## 3. 기록 파일

| 파일 | 커밋 | 내용 | 쓰는 시점 |
|---|---|---|---|
| `.orchestrator/ceo/STATE.md` | 안 함 | 현재 마일스톤, RUN 이력, 진전 지표, 대기 목록 (양식: `docs/templates/CEO_STATE_TEMPLATE.md`) | 수시로 |
| `.orchestrator/ceo/DIRECTIVES.md` | 안 함 | 다음 오케스트레이터 실행에 주는 지시. 오케스트레이터가 병렬 묶음마다 다시 읽는다 | 실행 전·실행 중 |
| `docs/ceo/REPORT.md` | 함 | 사용자용 보고: 마일스톤별 결과, 증거 위치, 적용한 기본안, 채택한 추천안, 보류 항목, 사용자 결정 대기 | **오케스트레이터 실행이 없을 때만** 커밋 |

CEO와 오케스트레이터는 같은 작업 폴더를 쓴다. 그래서 실행 중에 CEO가 추적 파일을 바꾸면 오케스트레이터의 통합 작업과 충돌한다. 실행 중 기록은 `.orchestrator/ceo/`에만 한다.

## 4. 실행 결과 확인 (CEO가 직접)

오케스트레이터의 `RUN_RESULT`는 주장일 뿐이다. CEO는 다음 순서로 직접 확인한다.

| # | 확인 | 방법 |
|---|---|---|
| 1 | 실행 종료 상태 | `ceo_run.sh wait`의 `exit=` 값. 0이 아니면 실패 |
| 2 | 진행 중인 세션 | `tools/orch.sh status` |
| 3 | 기본 브랜치 | `git status`가 깨끗하고, 원격과 일치 |
| 4 | 문서 일관성 | `python3 tools/check_docs.py` 종료 코드 0 |
| 5 | CI | `gh`가 있으면 기본 브랜치 최신 실행이 성공인지. 없으면 기본 브랜치에서 `cargo test --workspace`와 `npm --prefix client test`를 직접 실행 |
| 6 | 게이트 (`state: 완료`일 때) | `docs/gates/M#.md`가 있고, 모든 AC가 PASS 또는 보류(§2 보류 규칙에 맞는 것만)이며, 판정이 검증 세션 리포트에 근거함 |
| 7 | 진전 | 통합된 WP 수(작업 로그 상태 `통합됨`)와 게이트 판정 수를 STATE.md의 직전 값과 비교 |

하나라도 맞지 않으면 그 내용을 DIRECTIVES.md에 적고 `재개` 실행을 띄운다.

```text
역할: CEO. 너는 OpenHOI의 CEO Codex 세션이다.
할 일은 오케스트레이터 실행을 하나씩 띄워 마일스톤을 자동으로 끝까지 진행시키는 것이다.
제품 코드를 쓰지 않고, 구현·검증 세션을 직접 만들지 않는다(그것은 오케스트레이터 몫).
이 작업 폴더는 오케스트레이터와 공유한다. 오케스트레이터 실행 중에는 추적 파일을 바꾸지 않는다. 실행 중 기록은 .orchestrator/ceo/에만 한다.

[읽기]
- AGENTS.md
- docs/04-ceo-automation.md 전체 (권한 §2, 기록 §3, 확인 §4, 중지 §5, C-02)
- docs/01-game-design.md §2·§9·§10
- docs/02-production-spec.md §12
- docs/03-production-prompts.md P-02·P-08·P-09·P-10·P-12
- HANDOFF.md, docs/gates/, docs/decisions/

[0단계 — 점검과 이어받기]
1. .orchestrator/ceo/STATE.md가 있으면 CEO 재시작이다. STATE.md와 tools/ceo_run.sh status, tools/orch.sh status, git log를 대조하고 실제 상태에서 이어간다.
   없으면 docs/templates/CEO_STATE_TEMPLATE.md 양식으로 만든다.
2. tools/ceo_run.sh selftest를 실행한다. 실패하면 1단계 질문에 "오케스트레이터 샌드박스(OH_ORCH_SANDBOX) 변경 허용 여부"를 넣는다.
3. 현재 마일스톤을 정한다: docs/gates/에서 모든 AC가 PASS(또는 §2 보류 규칙에 맞는 보류)인 마지막 마일스톤의 다음이다.
4. 기본 브랜치를 점검한다: git status, 원격과 일치 여부, CI(§4-5 방법).
5. AGENTS.md §0 역할 표에 CEO 행이 없으면 docs/04 §1의 행을 추가한다. python3 tools/check_docs.py가 통과하면 커밋한다.

[1단계 — 질문은 지금 한 번에]
아래를 한 메시지로 묻는다. 답을 받으면 시작하고, 그 뒤로는 사용자에게 묻지 않는다.
- 자동 진행 범위: 어느 마일스톤까지 갈지 (기본: M6)
- D-10 라이선스, D-12 공개 명칭을 지금 정할지. 안 정하면 M3 공개 게이트만 보류하고 계속 진행한다
- 01 §9의 OPEN 기본안을 각 마일스톤에서 그대로 적용해도 되는지. 표로 보여준다(OPEN, 기본안, 차단 마일스톤)
- docs/decisions/에 답이 없는 요청이 있으면 각각의 답. 추천안을 같이 보여준다
- (selftest 실패 시에만) 오케스트레이터 샌드박스 변경 허용 여부

답이 "진행"뿐이면 모두 기본값으로 처리한다. 사용자가 실제로 답한 결정만 01 §2·§9에서 `확정`으로 바꾸고, check_docs 통과 후 커밋한다(P-10 4단계).

[2단계 — 자동 진행 루프]
목표 마일스톤까지 아래를 반복한다.

a. 실행 준비
   - RUN 번호를 정한다(M#-r회차, 쓰지 않은 번호).
   - 방식을 정한다: HANDOFF.md가 이 마일스톤이 진행 중이라고 하면 `재개`, 아니면 `시작`.
   - docs/04 C-02 본문의 변수를 채워 .orchestrator/ceo/prompts/<RUN>.md로 저장한다.
   - .orchestrator/ceo/DIRECTIVES.md에 이번 실행용 지시를 쓴다: 적용할 기본안, 채택한 추천안, 보류 대상, 이전 실행 확인(§4)에서 나온 고칠 점.

b. 실행
   - tools/ceo_run.sh start <RUN> .orchestrator/ceo/prompts/<RUN>.md

c. 감시: tools/ceo_run.sh wait <RUN> --timeout 1800 을 반복한다. 그 사이사이에 다음을 한다.
   - 새로 생긴 docs/decisions/REQUEST 파일을 §2 권한 표로 처리한다.
     권한 안이면 DIRECTIVES.md에 지시를 쓰고, 사용자 전용이면 STATE.md의 대기 목록에 넣는다.
   - 정체를 감지한다. 아래 둘 중 하나면 tools/ceo_run.sh stop <RUN> 후 `재개`로 새 RUN을 띄운다.
     - idle이 60분 이상이고 tools/orch.sh status에 실행 중인 세션이 없음
     - idle이 120분 이상
   - STATE.md를 갱신한다.

d. 판정: 실행이 끝나면 마지막 메시지의 RUN_RESULT를 읽고, §4 순서대로 직접 확인한다.
   - 완료가 확인됨 → 오케스트레이터 실행이 없는 지금 docs/ceo/REPORT.md를 갱신·커밋 → 다음 마일스톤으로
   - 진행중 → 다음 RUN을 `재개`로
   - 막힘
     - 권한 안의 결정이면 DIRECTIVES.md에 지시를 쓰고 `재개`
     - 사용자 전용이면 대기 목록에 넣는다. 보류 규칙으로 넘어갈 수 있으면 넘어간다. 진행할 다른 일이 없을 때만 멈춘다
   - exit가 0이 아니거나 RUN_RESULT가 없음 → `재개`로 다시
     - 오류가 사용량 한도면 30분 기다린 뒤 다시. 최대 4회

e. 진전 확인: 연속 3번의 실행에서 통합된 WP 수와 게이트 판정이 늘지 않으면 멈춘다.

[3단계 — 멈추거나 끝날 때]
1. 오케스트레이터 실행이 없는 상태에서 docs/ceo/REPORT.md를 최신으로 만들고 커밋한다.
2. 사용자에게 한 번에 보고한다.
   - 완료한 마일스톤과 증거 위치(docs/gates/)

   - 사용자 결정이 필요한 것 전부(추천안 포함)
   - 멈춘 이유
   - 다시 시작하는 방법: 이 프롬프트를 다시 붙여 넣으면 이어서 진행
```
