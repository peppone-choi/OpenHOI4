# M2 재개 계획

2026-10-08 사용자 재개 지시에 따른 계획이다. 이전 내부 실행 원장이나 부분 P07 결과를 복원한 문서가 아니다. 기준 소스는 `743c2a941af5422b94e850b6064b19cffbebac31`이며 M2는 미완료다.

## 먼저 인수할 범위

WP-14 경제·정치의 현재 producer를 새로운 독립 검증으로 인수한다. 규칙은 01 §4.3의 CEO 한정 잠정, 기술 경계는 02 §5.11·§6.2와 `docs/technical-notes.md`를 따른다. 후속 생산·훈련·항복 consumer까지 완료로 확대하지 않는다.

| 단계 | 작업 | 인수 조건 |
|---|---|---|
| 1 | 원격 main·입력 fixture·도구 버전 확인 | 정확한 기준 커밋, 두 fixture manifest의 경로·길이·해시, Rust 1.99.0 |
| 2 | 새 WP-14 독립 검증 | schema·formula·경제/정치 단위 검사, save v5·wire·query, 실패 원자성 |
| 3 | 실제 CLI/server 복원 | level4의 `economy:TargetConflict`, MIN target의 `economy:InvalidValue`, 유효 target2 control. normal/force와 실제 상태를 구분 |
| 4 | P07 통합 검사 | workspace 검사, 결정론 두 번, 저장·새 프로세스 재개·legacy, 클라이언트 검사·별도 서버 연동, active 팩 strict validation |
| 5 | 판정 | 새 독립 PASS와 같은 main CI 녹색을 함께 확인. 막힌 검사는 원인과 미실행 범위를 기록 |

restore-stage와 target-range는 다른 팩 입력을 사용한다. 각각 22파일/5681bytes와 22파일/5617bytes이며 CRLF·save/header/pack identity를 보존한다. PackMismatch나 panic을 기대한 의미 거부로 계산하지 않는다. 과거 P07 실행 번호를 새 검사 번호나 완료 판정으로 재사용하지 않는다.

## WP-14 인수 뒤의 병렬 작업

각 구현·검증 담당은 별도 worktree에서 작업하며, 동시에 구현하는 WP는 세 개 이하로 둔다. 검증 담당은 구현에 참여하지 않고 추적 파일을 바꾸지 않는다.

| WP | 첫 범위 | 병렬 가능한 작업 | 선행·보류 경계 |
|---|---|---|---|
| WP-23 | 6개국·100~200 프로빈스의 독립 합성 Testland 초기 콘텐츠 | 지도·국가·주·ko/en 현지화·출처와 입력 검증 | WP-14 producer 인수 뒤 착수. 장비·대대 등은 실제 producer schema 인수 뒤 작성. M1·골든 fixture를 대체하지 않음 |
| WP-15 | 장비 정의·국가 비축·생산 라인 | 생산 전용 모듈·독립 공식/경계 테스트·schema 설계 | WP-14 인수 뒤 착수. REQ-ECO-03·REQ-MIL-01과 01 §4.3을 따르며 미정 게임 규칙을 임의 채택하지 않음 |
| WP-19 | 수도·보급 거점·항구, 수도로 연결된 철도 용량, 이동 비용 거리 감쇠·포위 | 보급 전용 모듈·독립 그래프/용량 테스트·schema 설계 | WP-14·WP-17 실제 계약 인수. 사단·전투 consumer와 M4 차량 소모를 구현 완료로 주장하지 않음 |

공유 schema·canonical/hash·save·protocol·TS 생성물 변경은 **WP-15 → WP-19 → WP-23의 최종 콘텐츠 인수** 순으로 직렬 통합한다. 각 담당은 변경 전에 필드의 의미·단위·범위·참조·권위·수명·실패 원자성·hash/save/wire/UI 대응과 독립 경계 예제를 설계한다. 뒤 담당은 앞 담당의 실제 커밋과 계약을 인수한다. 비공유 콘텐츠·전용 모듈 준비는 병렬로 진행할 수 있다.

WP-16은 WP-15 뒤다. 전투·외교·AI는 해당 선행 WP의 인수 뒤에 진행한다. UI나 실제 consumer가 없는 내부 모델을 플레이 가능한 기능으로 기록하지 않는다. 기존 None/v1~v5 저장·fixture·원 bytes·해시와 오류 계약을 보존하며 호환 파괴·migration은 별도 결정이 필요하다.

## 실행 배정

아래는 인수 통과 뒤 사용할 배정이다. 브랜치·worktree를 이미 만들었거나 구현을 실행했다는 기록이 아니다. 실제 시작 전에 기준 main과 담당 범위를 다시 확인한다.

| 유형 | 브랜치/담당 | 소유 경로 | 실행·검증 |
|---|---|---|---|
| WP-23 콘텐츠 구현 | `wp/23-testland-cloud` | 새 M2 합성 팩·그 팩의 현지화/출처. 기존 골든/M1 입력 수정 금지 | 별도 구현 세션·worktree. P11 뒤 새 P05 검증 세션 |
| WP-15 구현 | `wp/15-production-cloud` | 생산 전용 모듈·관련 정의/테스트. 공유 schema/save/protocol은 직렬 배정 | P03/P06 별도 구현 세션·worktree. 구현 커밋을 분리한 새 P05 worktree |
| WP-19 구현 | `wp/19-supply-cloud` | 보급 전용 모듈·관련 정의/테스트. 공유 경로는 WP-15 인수 뒤 배정 | P03/P06 별도 구현 세션·worktree. 구현 커밋을 분리한 새 P05 worktree |
| 오케스트레이터 | 계획·통합 담당 | 계획·handoff·검증 요약·추적 매트릭스 | 제품 구현에 참여하지 않고 P07 검사·CI와 통합 순서를 관리 |

이 환경에서는 앱의 독립 세션과 지정 Git worktree를 사용한다. 하위 CLI 인증·전역 설정을 새로 만들지 않는다. 실행은 지정 worktree 절대 경로에서 하고, 검증 전후 HEAD·추적 파일 목록·diff/status가 같아야 유효하다. 구현과 검증의 실제 담당을 배정한 뒤에만 시작 상태를 기록한다.

## 오케스트레이터 작업과 결정

검증 중에는 도구와 CI 확인, 다음 WP 프롬프트·공유 변경 순서 준비를 진행한다. 오류는 P06 구현 담당에게 재현과 함께 전달하고 수정 뒤 새 독립 검증을 한다. 규칙이 모호하면 선택지와 추천안을 모아 사용자 결정으로 넘기며, 그 결정과 독립인 작업은 계속한다. D·OPEN 상태는 사용자 답 없이 바꾸지 않는다.

원 실행 로그·raw API·증거 압축파일은 Git에 넣지 않는다. 공개 문서에는 실제 검사 요약·재현 명령·남은 범위만 남긴다. 미병합 브랜치·worktree와 원 사용자 작업은 보존한다. main CI가 녹색이라는 사실만으로 WP-14 인수나 M2 게이트를 PASS로 판정하지 않는다.
