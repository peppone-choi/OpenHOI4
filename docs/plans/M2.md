## 시작 상태와 목표

M0·M1 독립 게이트 PASS를 보존한다. 시작 main은 `227a971101338ba3195599bb042c8570dd0365e9`이며 이전 `428a53d` 네 CI 성공과 구분한다. 227 CI/Core/Simulation/Save의 현재 결과는 실행 증거에서 관측한다. M2 제품은 미착수다. CLI selftest HTTP400/exit1과 앱 실행은 별개다. 실행 환경·모델·승인·네트워크 설정은 바꾸지 않는다.

목표는 W1 WP-13/17/24/25와 W2 WP-14/23을 구현 앱 → 새 exact 독립 검증 앱 → P-07 → 같은 main HEAD CI 순서로 통합하는 것이다. 전체 M2 게이트 AC 7개와 필수 REQ 48개는 후속 W3~W7까지 필요하며 이번 W1/W2로 전체 완료를 선언하지 않는다.

각 P-03은 코드 변경 전에 `docs/plans/WP-NN-schema.md`에 필드 표·참조 그래프·독립 경계 입력/기대값을 작성한다. [공통 기획](schema-planning.md)과 [M2 공유 계약](M2-contracts.md)을 적용한다. 담당자는 설계 기록 후 구현하며 P-05는 같은 정확 문서를 검사한다. 기초 M1을 최종 국가·주·군사 모델로 쓰지 않는다.

M0 팩/golden·기존 M1 시나리오·v1 save fixture/hash는 보존한다. M2 필드를 v1 binary 구조에 무조건 덧붙이지 않는다. 구 저장 거부·호환 파괴·기존 fixture 교체·migration은 승인되지 않았다. 독립적으로 추가된 새 상태의 별도 포맷/decoder는 기존 v1 읽기·쓰기/hash를 유지하는 구체 설계와 호환 fixture가 먼저 필요하다. 호환이 확실하지 않은 경로는 P-10으로 기록하고 독립 부분을 진행한다. 미지원 게임 효과는 명시 인터페이스와 후속 WP로 남기며 성공한 것처럼 처리하지 않는다.

## 검증·통합

구현 앱은 전용 worktree/브랜치에서 커밋까지 한다. 정상 final·clean HEAD·작업로그·실제 producer 출력이 확인된 뒤 새 검증 앱과 정확 커밋 detached worktree를 만든다. 최초 검증 baseline은 앱 생성 전에 부모가 저장한다. HEAD/index semantic·raw index bytes/추적 목록·각 파일 SHA256/diff/cached/status가 전후 동일해야 유효하다. baseline을 덮거나 index를 복구해 불변성을 꾸미지 않는다. 원 final 전문과 명령 로그·검증 산출물을 SHA manifest로 보존한다. 앱 종료에 CLI exit0을 쓰지 않는다.

검증 FAIL 원문은 유지하고 P-06 뒤 새 P-05를 한다. PASS 브랜치만 P-07로 통합한다. 네 CI 및 모든 필수 job이 같은 main HEAD에서 성공해야 통합됨이다. W1-a 통합 순서는 WP-24 → WP-17이고 W1 전체는 WP-24 → WP-17 → WP-13 → WP-25다. W2는 WP-14 → WP-23이다. 간단한 병합만 부모가 처리하며 코드 판단 충돌은 구현자에게 인계한다.

직접 UI 평시→전쟁→항복, AI 50회, 원장·3OS·M2 save/repro·성능 기준선과 01 §11은 M2 최종 게이트 요구다. W1 이동 인터페이스를 전체 편제/UI/전투 완료로 기록하지 않는다. 과거 DPR timeout과 Edge 최초 화면 원인은 미확정 상태를 보존한다.
