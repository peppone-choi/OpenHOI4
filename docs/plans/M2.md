# M2 재개 계획

2026-10-08 사용자 재개 지시에 따른 계획이다. 이전 내부 실행 원장이나 부분 P07 결과를 복원한 문서가 아니다. 기준 소스는 `743c2a941af5422b94e850b6064b19cffbebac31`이며 M2는 미완료다.

## 먼저 인수할 범위

WP-14 경제·정치의 현재 producer를 새로운 독립 검증으로 인수한다. 규칙은 01 §4.3의 CEO 한정 잠정, 기술 경계는 02 §5.11·§6.2와 `docs/technical-notes.md`를 따른다. 후속 생산·훈련·항복 consumer까지 완료로 확대하지 않는다.

| 단계 | 작업 | 인수 조건 |
|---|---|---|
| 1 | 원격 main·입력 fixture·도구 버전 확인 | 정확한 기준 커밋, 두 fixture manifest의 경로·길이·해시, Rust 1.99.0 |
| 2 | 새 WP-14 독립 검증 | schema·formula·경제/정치 단위 검사, save v5·wire·query, 실패 원자성 |
| 3 | 실제 CLI/server 복원 | level4의 `economy:TargetConflict`, MIN target의 `economy:InvalidValue`, 유효 target2 control. normal/force와 실제 상태를 구분 |
| 4 | P07 통합 검사 | workspace 검사, 결정론 두 번, 저장·새 프로세스 재개·legacy, 클라이언트 검사·별도 서버 연동, active 팩 strict validation |
| 5 | 판정 | 새 독립 PASS와 같은 main CI 녹색을 함께 확인. 막힌 검사는 원인과 미실행 범위를 기록 |

restore-stage와 target-range는 다른 팩 입력을 사용한다. 각각 22파일/5681bytes와 22파일/5617bytes이며 CRLF·save/header/pack identity를 보존한다. PackMismatch나 panic을 기대한 의미 거부로 계산하지 않는다. 과거 P07 실행 번호를 새 검사 번호나 완료 판정으로 재사용하지 않는다.

새 환경의 최초 검증은 유효 target2 서버의 WebSocket Close 종료 오류로 FAIL이었다. 별도 P06 수정 뒤 소스 `4ae0446a01487e9d6d1415e7191a78407a8e0b6f`를 구현 비참여 새 세션이 검증하여 지정한 producer·P07 repair 범위 PASS를 판정했다. [검증 요약](../verify/WP-14-P07-cloud-repair.md)을 따른다. [PR #2](https://github.com/peppone-choi/OpenHOI4/pull/2)는 main `0776e6b5a67951821860490964c402e518310ca5`로 정상 병합됐고 같은 main의 CI 7개는 모두 success다. 지정한 producer·repair 통합 인수 뒤 독립 초기 콘텐츠만 착수했다. M2 완료를 의미하지 않는다.

## WP-14 인수 뒤의 병렬 작업

각 구현·검증 담당은 별도 worktree에서 작업하며, 동시에 구현하는 WP는 세 개 이하로 둔다. 검증 담당은 구현에 참여하지 않고 추적 파일을 바꾸지 않는다.

| WP | 첫 범위 | 병렬 가능한 작업 | 선행·보류 경계 |
|---|---|---|---|
| WP-23 | 6개국·100~200 프로빈스의 독립 합성 Testland 초기 콘텐츠 | 지도·국가·주·ko/en 현지화·출처와 입력 검증 | WP-14 producer 인수 뒤 착수. 장비·대대 등은 실제 producer schema 인수 뒤 작성. M1·골든 fixture를 대체하지 않음 |
| WP-15 | 장비 정의·국가 비축·생산 라인 | 생산 전용 모듈·독립 공식/경계 테스트·schema 설계 | WP-14 인수 뒤 착수. REQ-ECO-03·REQ-MIL-01과 01 §4.3을 따르며 미정 게임 규칙을 임의 채택하지 않음 |
| WP-19 | 수도·보급 거점·항구, 수도로 연결된 철도 용량, 이동 비용 거리 감쇠·포위 | 보급 전용 모듈·독립 그래프/용량 테스트·schema 설계 | WP-14·WP-17 실제 계약 인수. 사단·전투 consumer와 M4 차량 소모를 구현 완료로 주장하지 않음 |

공유 schema·canonical/hash·save·protocol·TS 생성물 변경은 **WP-15 → WP-19 → WP-23의 최종 콘텐츠 인수** 순으로 직렬 통합한다. 각 담당은 변경 전에 필드의 의미·단위·범위·참조·권위·수명·실패 원자성·hash/save/wire/UI 대응과 독립 경계 예제를 설계한다. 뒤 담당은 앞 담당의 실제 커밋과 계약을 인수한다. 비공유 콘텐츠·전용 모듈 준비는 병렬로 진행할 수 있다.

WP-16은 WP-15 뒤다. 전투·외교·AI는 해당 선행 WP의 인수 뒤에 진행한다. UI나 실제 consumer가 없는 내부 모델을 플레이 가능한 기능으로 기록하지 않는다. 기존 None/v1~v5 저장·fixture·원 bytes·해시와 오류 계약을 보존하며 호환 파괴·migration은 별도 결정이 필요하다.

## 실행 배정

WP-23 초기 콘텐츠 구현은 인수된 main `0776e6b5a67951821860490964c402e518310ca5` 기반의 지정 worktree에서 실행했고 `b7c5b6898855a136456f7b558724f18cafa0656b`로 커밋했다. 새 독립 담당의 분리된 같은 commit worktree 검증은 지정한 초기 범위 PASS다. [검증 요약](../verify/WP-23-initial-cloud.md)을 따르며, 초기 콘텐츠 독립 PASS·같은 main CI 통합·최종 WP-23/M2 판정을 구분한다. [PR #3](https://github.com/peppone-choi/OpenHOI4/pull/3)는 main `b112291c11822ffbf6da33b42670ff5cdb226fae`로 병합됐고 같은 main CI 7개 모두 success다. 지정한 초기 콘텐츠 통합 게이트를 충족했다. WP-15는 공유 schema/save/protocol 첫 slot에서 구현 커밋 `c7b404a96c685068e6e79c79fecad4be3b42fd95`를 작성했다. 실제 combined tree `95e674407aa820de14249a84bea160eba2728019`의 한 번의 새 독립 검증은 중복 allowed_models schema/parser 불일치 한 건으로 FAIL이었다. P06 수정의 통합 후보 `40f703cf331125abc4d3b78f431e6f7fc7253476`에서 해당 경계만 표적 확인해 독립 QA 게이트 PASS를 확보했다([검증 요약](../verify/WP-15-production-cloud.md)). ## WP-19 등록·World/Map 후속 단위

사용자가 WP-15 인수 뒤 승인한 다음 단위다. 기준은 main `6d1d1d9278c7771be9b9ba2943e745a9094b9104`, 구현은 `ae5bfba50e7dab59c93a28fee620ec17cf68059c`, 독립 검증 후보는 `7cbb5572c0a11dfb279016ddafb95777bb53456b`다. 모듈 등록·실제 World/Map의 순수 네트워크 입력만 다루며 한 번의 새 독립 검증에서 지정 범위 PASS를 받았다([검증 요약](../verify/WP-19-world-adapter-cloud.md)). 전후 571개 추적 파일·HEAD·diff/status가 같았고 workspace Rust 306개·clippy·독립 방향 경로/실제 World 공식 검사가 통과했다. PR·같은 main CI는 후속 통합 게이트다. 공급 알고리즘이 일반 Cargo에서 컴파일되는 것과 실제 daily consumer가 연결되는 것은 각각 증거로 판정한다.

공유 소스 변경은 `oh_sim/lib.rs`의 등록 한 줄과 supply 모듈·전용 테스트로 제한한다. canonical state·기존 schema/save/protocol·클라이언트·M1/M2 팩·golden·lock은 유지한다. 방향별 비용은 목적지 terrain·river·현재 owning-state infrastructure를 기존 `movement_hours` 순서로 계산한다. 철도 capacity는 무방향으로 공유하며 경로는 기존 widest → shortest → 전체 경로 순 정렬을 유지한다. `None`을 국가0으로 바꾸지 않으며 실제 통제국으로 연결을 판정한다.

전세계 infrastructure 계수 curve는 미정이므로 현재 level에 대응하는 명시 양수 표가 필수다. 누락·stale context는 오류다. 추천은 실제 supported levels를 데이터에 명시한 exact table부터 인수하고 fractional interpolation 정책은 별도 결정하는 것이다. 유효 World는 육상 controllerNone을 만들거나 복원하지 않으므로 실제 waterNone·국가0·owner와 다른 controller, 그래프의 landNone 차단을 각각 검사한다. hub/port 배치 권위는 없으므로 집계 건물이나 coastal만으로 위치를 만들지 않는다. 명시 static rails는 건설·손상 상태가 아니다.

다음 producer는 WP-16의 실제 사단·편제·수요·strength/org/attack/lifetime 계약이다. 실제 이동의 현재/다음 leg 효과, 새 daily 원장·원자성·canonical/save·wire/query·served UI는 별도 단위로 분리한다. 현재 V6는 production presence를 요구하므로 supply-only mode에 빈 Production을 주입하는 식으로 save 경계를 숨기지 않는다. 본 단위는 Network만 반환하며 빈 demand로 Day를 만들어 실제 기능으로 표시하지 않는다. 전체 WP-19/M2 인수는 후속이다.

## 오케스트레이터 작업과 결정

검증 중에는 도구와 CI 확인, 다음 WP 프롬프트·공유 변경 순서 준비를 진행한다. 변경 단위마다 새 독립 검토를 한 번 수행한다. 발견한 오류는 P06 구현 담당에게 재현과 함께 전달하고 수정 범위에 맞는 검사로 확인하며, 같은 단위의 전체 검토를 반복하지 않는다. 규칙이 모호하면 선택지와 추천안을 모아 사용자 결정으로 넘기며, 그 결정과 독립인 작업은 계속한다. D·OPEN 상태는 사용자 답 없이 바꾸지 않는다.

2026-10-08 사용자가 생산 소수 이월·실제 생산 때만 효율 성장·다른 모델 전환 시 미완성량 폐기·부족 자원 비례 배분과 보급 공유 철도 용량·거리 손실·첫 버전 고정 경로를 승인했다. 초기 데이터 수치의 선택·검증은 위임됐으며 단위·반올림·민감도와 provisional 상태를 각 ADR에 남긴다. 승인과 일치하는 기술 선택은 진행하고 실질적 충돌이나 미인수 실제 producer 계약은 보고한다. WP-19 actual division demand/strength/org/attack, terrain/infra 이동 비용과 현재/다음 leg, strict building/coastal port 입력, additive save/query 계약은 아직 인수하지 않았다. 기존 phase marker나 이동 time multiplier를 실제 생산·보급 consumer로 계산하지 않는다. WP-23의 장비·대대 최종 콘텐츠는 실제 producer 인수 뒤 작성한다.

원 실행 로그·raw API·증거 압축파일은 Git에 넣지 않는다. 공개 문서에는 실제 검사 요약·재현 명령·남은 범위만 남긴다. 미병합 브랜치·worktree와 원 사용자 작업은 보존한다. main CI가 녹색이라는 사실만으로 WP-14 인수나 M2 게이트를 PASS로 판정하지 않는다.
